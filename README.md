# ChatServer

A simple WebSocket chat server built with TypeScript. Plain HTTP requests return a small JSON health payload, while WebSocket connections relay every chat message to all other connected clients.

│   └── tasks.json       # Build / dev / clean tasks

## Requirements

- Node.js 18 or newer

## Getting started

Install dependencies:

```bash
npm install
```

### Develop (auto-reload)

Run in watch mode — the server restarts whenever a source file changes:

```bash
npm run dev
```

### Build & run

Bundle the server into a single file with webpack and run it:

```bash
npm run build
npm start
```

The bundle is written to `dist/index.js` along with `dist/index.js.map`. Dependencies
such as `ws` are bundled in, so `dist/` is self-contained (aside from optional native
accelerators like `bufferutil`/`utf-8-validate`, which are loaded if installed).

Other build commands:

```bash
npm run build:dev   # Development bundle (unminified, with source maps)
npm run watch       # Rebuild on file changes
npm run typecheck   # Type-check without emitting output
```

Once running, the server listens on `http://0.0.0.0:3000` by default. The port, host, and
welcome message are read from your per-user config file; see [Configuration](#configuration)
for details, including environment variable and CLI overrides:

```bash
PORT=8080 HOST=localhost npm start
```

## Configuration

Settings live in a per-user config folder. On first run the folder and `config.json` are
created automatically with the defaults, so you can edit them afterwards and restart the
server.

| Platform | Default folder |
| -------- | -------------- |
| macOS | `~/Library/Application Support/chatserver` |
| Linux | `$XDG_CONFIG_HOME/chatserver` (or `~/.config/chatserver`) |
| Windows | `%APPDATA%\chatserver` |

A config folder contains:

```
~/Library/Application Support/chatserver/
├── config.json          # required; created with defaults on first run
└── websocket_ignore     # optional; one per messager that uses ignore-sender
```

Example `config.json`:

```json
{
  "host": "0.0.0.0",
  "port": 3000,
  "welcomeMessage": "Connected to ChatServer",
  "chats": [
    { "name": "lobby", "messager": "websocket", "filters": [] },
    {
      "name": "quiet",
      "messager": {
        "type": "websocket",
        "options": { "path": "/ws/quiet", "welcomeMessage": "Quiet room" }
      },
      "filters": ["ignore-sender"],
      "replyWhenOptional": true
    }
  ]
}
```

| Option | Type | Description |
| ------ | ---- | ----------- |
| `host` | string | Address to bind to. Use `127.0.0.1` to accept local connections only. |
| `port` | integer | Listen port, 1–65535. |
| `welcomeMessage` | string | Default system message sent to each client on connect. |
| `chats` | array | Chat pipelines. Omitting it serves one default WebSocket chat. |

### Chats

Each entry in `chats` selects a registered messager and a list of filters by name:

| Field | Type | Description |
| ----- | ---- | ----------- |
| `name` | string | Unique chat name. Defaults to `chat-1`, `chat-2`, … |
| `messager` | string or object | Messager implementation. Defaults to `websocket`. |
| `filters` | array | Filters applied in order. Defaults to `[]` (reply to everything). |
| `replyWhenOptional` | boolean | Fallback when every filter returns `'optional'`. Defaults to `true`. |

A messager or filter may be written as a plain name (`"websocket"`) or with options:

```json
{ "type": "ignore-sender", "options": { "file": "lobby_ignore" } }
```

Available implementations:

| Kind | Name | Options |
| ---- | ---- | ------- |
| messager | `websocket` | `path` (string), `welcomeMessage` (string) |
| filter | `allow-all` | none |
| filter | `ignore-sender` | `file` (string), `senderIds` (string array) |

WebSocket paths default to `/` when one chat is configured and `/ws/<name>` when several
chats share the process, so multiple chats can be used at once without extra configuration.
Set `options.path` to choose your own.

### Ignore list file

`ignore-sender` reads its sender IDs from a file named `<messager>_ignore` in the config
folder. With the default `websocket` messager, that is `websocket_ignore`:

```
~/Library/Application Support/chatserver/websocket_ignore
```

The file holds comma-separated sender IDs. Newlines also separate entries, so one ID per
line works, and `#` lines are comments:

```
# Senders that should not get replies
client-1, client-2
client-7
```

- A missing file means nobody is ignored.
- The file is re-read when it changes (checked about once per second), so edits apply
  without restarting the server.
- Set `options.file` to use a different file. Relative paths resolve against the config
  directory; absolute paths are used as-is.
- `options.senderIds` may still be used for small inline lists. Inline IDs are combined
  with the file.

Chats that use the same messager type share the same file by default. Give each chat its
own `options.file` when they need separate lists.

Unknown adapter names, duplicate chat names, duplicate WebSocket paths, and invalid
option values cause startup to fail with a message listing what is available.
Unknown keys are ignored with a warning; invalid values cause the server to exit with
a clear error instead of silently falling back to defaults.

### Precedence

1. Environment variables (highest)
2. Config file
3. Built-in defaults

```bash
CHATSERVER_CONFIG_DIR=/path/to/config-dir   # config folder
CHATSERVER_HOST=127.0.0.1                    # or HOST
CHATSERVER_PORT=8080                         # or PORT
CHATSERVER_WELCOME_MESSAGE="Hi there"
```

`PORT` and `HOST` remain supported for backwards compatibility.

### CLI options

```bash
chatserver --config_dir ./my-folder   # use a specific config folder
chatserver --print-config             # show the resolved paths and values, then exit
chatserver --help
```

`--config_dir` (also `-c`, or `CHATSERVER_CONFIG_DIR`) takes a **directory**. It must
already exist and contain `config.json`. Any `<messager>_ignore` files in that directory
are used by the `ignore-sender` filter. You cannot point the option at a file.

When `--config_dir` is omitted, the per-user config folder is used and is created on
first run with a default `config.json`.

```
my-folder/
├── config.json          # required
└── websocket_ignore     # optional; one per messager that uses ignore-sender
```

`--print-config` shows the resolved `configPath`, `configDir`, and effective values.

## Adapters

The server core is transport- and policy-agnostic. It depends on two adapter interfaces,
each in its own folder. Every folder has an `interface.ts` holding the contract, plus one
file per implementation. All of them are re-exported from `src/server.ts`.

| File | Contents |
| ---- | -------- |
| `filters/interface.ts` | `FilterAdapter` interface and filter chain evaluation |
| `filters/allow-all.ts` | `AllowAllFilter` |
| `filters/ignore-sender.ts` | `IgnoreSenderFilter` |
| `filters/ignore-file.ts` | `IgnoreFile` file-backed sender list and parser |
| `filters/registry.ts` | Name → filter factory registry |
| `messagers/interface.ts` | `MessagerAdapter` interface and message types |
| `messagers/websocket.ts` | `WebSocketMessagerAdapter` and `WebSocketHub` |
| `messagers/registry.ts` | Name → messager factory registry |

Implementations are registered by name so the config file can select them. To add your
own, register it at startup before loading the config:

```ts
import { registerFilter, registerMessager } from './server';

registerFilter('my-filter', (options) => new MyFilter(options));
registerMessager('my-transport', (options, context) => new MyTransport(context.server));
```

The `chats` array in the config file then references `"my-filter"` / `"my-transport"`
by name.

### Messager adapter

`MessagerAdapter` receives inbound messages and delivers replies, so the transport can be
swapped (WebSocket, stdin/stdout, a queue, etc.).

```ts
export interface MessagerAdapter {
  readonly name: string;
  start(handler: (message: IncomingMessage) => void): void | Promise<void>;
  reply(message: IncomingMessage, reply: OutgoingMessage): void | Promise<void>;
  stop?(): void | Promise<void>;
}
```

`IncomingMessage` carries normalized `text`, a `senderId`, an optional `channel`, and
adapter-specific `metadata`. `OutgoingMessage` carries the reply `text`, an optional
`channel`, and a `direct` flag (direct reply to the sender instead of a broadcast).

`WebSocketMessagerAdapter` is the default implementation. It attaches to the HTTP server,
sends the welcome message, assigns each connection a `senderId`, and broadcasts replies to
all other clients unless `direct` is set.

### Filter adapter

`FilterAdapter` decides whether an inbound message should be replied to. It returns
`true`, `false`, or `'optional'`:

```ts
export type FilterResult = boolean | 'optional';

export interface FilterAdapter {
  readonly name: string;
  shouldReply(message: IncomingMessage): FilterResult | Promise<FilterResult>;
}
```

- `true` — reply to the message.
- `false` — do not reply.
- `'optional'` — no opinion; the next filter decides.

Filters run in order and the first decisive result wins. If every filter abstains (or no
filters are configured), the server replies by default; set `replyWhenOptional: false` to
change that. A filter that throws is treated as `false` (fail closed).

```ts
import { createChatServer } from './server';
import { IgnoreFile } from './filters/ignore-file';
import { IgnoreSenderFilter } from './filters/ignore-sender';

const server = createChatServer({
  filters: [new IgnoreSenderFilter(new IgnoreFile('./websocket_ignore'))]
});
```

`IgnoreSenderFilter` also accepts a fixed string array for simple cases.
`AllowAllFilter` is a minimal reference implementation. Adapters are plain objects, so
custom filters need only implement `shouldReply` in their own module.

## Models

`chatserver-models` manages OpenAI Responses API compatible providers and models. Provider
details live in `<config_dir>/models.json`; each provider's API key lives in the OS
credential manager under the provider name.

```bash
chatserver-models <command> [options]
```

| Command | Description |
| ------- | ----------- |
| `add` | Add a model to a provider and store the provider's API key |
| `test` | Send a prompt to a configured model |
| `list` | List configured providers and models |
| `update` | Change provider or model details, or rotate the API key |
| `remove` | Remove a model (and its provider once empty) |

Run `chatserver-models <command> --help` for command-specific options. Every command
accepts `--config_dir <dir>`, which defaults to `CHATSERVER_CONFIG_DIR` or the per-user
config folder.

API keys are never written to `models.json`:

| Platform | Credential store |
| -------- | ---------------- |
| macOS | Keychain (via `security`) |
| Linux | Secret Service (via `secret-tool` from libsecret) |
| Windows | Credential Manager (requires the `CredentialManager` PowerShell module) |

Credentials use the service name `chatserver-models` and the **provider name** as the
account, so every model from the same provider shares one key.

### Add a model

```bash
npm run model:add -- \
  --provider openai \
  --base-url https://api.openai.com/v1 \
  --model gpt-4.1-mini \
  --name gpt-mini
```

The provider is created when it does not exist yet. An existing provider's base URL and
API key are kept unless you pass `--base-url` or `--api-key`. When the provider has no
stored key, the key is read from `--api-key`, then `OPENAI_API_KEY`, then an interactive
prompt (input is hidden). Existing models are only replaced with `--force` or by
confirming the prompt.

`models.json` holds non-secret details:

```json
{
  "version": 1,
  "providers": [
    {
      "provider": "openai",
      "baseUrl": "https://api.openai.com/v1",
      "models": [
        { "id": "gpt-4.1-mini", "name": "gpt-mini" }
      ]
    }
  ]
}
```

### Test a model

```bash
npm run model:test -- --provider openai --name gpt-mini --prompt "Say hello."
```

Add `--json` to print the raw API response, or `--timeout <ms>` to change the 60-second
request timeout. The key comes from `CHATSERVER_MODEL_API_KEY` or the credential manager.

### List, update, and remove

```bash
npm run model:list --

npm run model:update -- --provider openai --base-url https://api.openai.com/v1
npm run model:update -- --provider openai --api-key sk-...          # rotate the key
npm run model:update -- --provider openai --name gpt-mini --model gpt-4.1
npm run model:update -- --provider openai --name gpt-mini --new-name mini

npm run model:remove -- --provider openai --name gpt-mini
```

When `remove` deletes a provider's last model, the provider entry is removed too and its
API key is deleted from the credential manager.

`list` prints a table with provider, model name, model id, and base URL; add `--json` for
raw JSON. `update` only changes the options you pass and fails when none are given.

When installed as a CLI the binary is `chatserver-models`, for example
`chatserver-models add --model gpt-4.1-mini`.

## Installing as a CLI (npx)

The package exposes a `chatserver` executable (`"bin": { "chatserver": "dist/index.js" }`),
so it can be invoked with `npx`.

### Install into another project

From the directory you want to use the command in (it must contain a `package.json`):

```bash
npm install /path/to/ChatServer
npx chatserver
```

This symlinks the local project into `node_modules`, and `npx` resolves the `chatserver`
binary from there. Because `dist/` is git-ignored, build once in the ChatServer directory
first (`npm run build`). The `prepare` script normally does this automatically, but some
npm versions block install scripts by default — run the build manually if prompted.

### One-off invocation without installing

```bash
npx --yes --package=/path/to/ChatServer chatserver
```

`--package` also accepts a packed tarball:

```bash
cd /path/to/ChatServer
npm pack                                  # creates chatserver-1.0.0.tgz (dist/ only)
npx --yes --package=/path/to/chatserver-1.0.0.tgz chatserver
```

### Make it globally available

```bash
cd /path/to/ChatServer
npm link
npx chatserver
```

Environment variables still apply in every form, for example:

```bash
PORT=8080 HOST=localhost npx chatserver
```

## Debugging

Two debug configurations are provided in `.vscode/launch.json` (press **F5** to start):

- **Debug Chat Server (ts-node)** — runs `src/index.ts` directly with `ts-node`; no build step required.
- **Debug Compiled Output (node)** — runs the webpack bundle at `dist/index.js`; automatically runs the `build` task first.

The webpack configurations emit source maps whose paths resolve back to `src/`, so
breakpoints set in your `.ts` files are hit correctly in both configurations.

## Linting

ESLint is configured in `eslint.config.mjs` with a TypeScript ruleset similar to
[`microsoft/vscode-cmake-tools`](https://github.com/microsoft/vscode-cmake-tools).

Check the codebase:

```bash
npm run lint
```

Automatically fix fixable issues:

```bash
npm run lint:fix
```

The configuration uses type-aware linting, so it can report issues such as floating
promises and misused promises. The ESLint VS Code extension will also surface these
diagnostics inline.
