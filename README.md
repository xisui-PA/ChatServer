# ChatServer

A TypeScript bridge for messager apps and LLM models. ChatServer runs adapter-based message pipelines without opening HTTP or WebSocket listening ports. Pipelines filter incoming messages and generate replies using configured LLM models; model management and testing are available through `chatserver-models`.

## Requirements

- Node.js 18 or newer

## Getting started

Install dependencies:

```bash
npm install
```

### Develop (auto-reload)

Run in watch mode — the server restarts whenever a source file changes:

```bash
npm run dev
```

### Build & run

Bundle the server into a single file with webpack and run it:

```bash
npm run build
npm start
```

The bundle is written to `dist/index.js` along with `dist/index.js.map`.

Other build commands:

```bash
npm run build:dev   # Development bundle (unminified, with source maps)
npm run watch       # Rebuild on file changes
npm run typecheck   # Type-check without emitting output
```

Configure the built-in `wechat` adapter to connect agent-wechat, or register custom
messager adapters before loading configuration.
The default configuration has no chats, so the process exits when there is no active
adapter keeping it alive. ChatServer does not bind a host or port.

## Configuration

Settings live in a per-user config folder. On first run the folder and `config.json` are
created automatically with the defaults, so you can edit them afterwards and restart the
server.

| Platform | Default folder |
| -------- | -------------- |
| macOS | `~/Library/Application Support/chatserver` |
| Linux | `$XDG_CONFIG_HOME/chatserver` (or `~/.config/chatserver`) |
| Windows | `%APPDATA%\chatserver` |

A config folder contains:

```
~/Library/Application Support/chatserver/
├── config.json           # required; created with defaults on first run
├── conversations/        # automatic; hashed per-conversation memory JSON files
└── my-messager_ignore     # optional; one per messager that uses ignore-sender
```

Default `config.json`:

```json
{ "chats": [] }
```

`chats` selects the message pipelines to run. Each configured chat must specify a
registered messager. The `wechat` implementation is bundled. `ChatServerOptions`
in `config.ts` defines this structure; each entry contains only `messager` and
`filters`. Log names (`chat-1`, `chat-2`, …) are generated from array positions.

### Chats

Each entry in `chats` selects a registered messager and a list of filters by name:

| Field | Type | Description |
| ----- | ---- | ----------- |
| `messager` | object | Required `name`, `replyer`; optional `mainAccount`, replier `tools`, and transport `options`. |
| `filters` | array | Filters applied in order. Defaults to `[]` (no filter decision). |

Messagers bind a chat-app transport to a reply model. Filters select an implementation
using `type`, with an additional `model` reference when `type` is `model`:

```json
{
  "messager": {
    "name": "wechat",
    "replyer": "my-provider/my-model-id",
    "mainAccount": "wxid_your_main_account",
    "tools": ["web_search", "read_url", "calculate", "current_time"],
    "options": { "tokenEnv": "AGENT_WECHAT_TOKEN" }
  },
  "filters": [
    { "type": "ignore" },
    {
      "type": "model",
      "model": "my-provider/my-filter-model-id",
      "options": { "instructions": "Allow questions; deny advertisements; otherwise abstain." }
    }
  ]
}
```

Available implementations:

| Kind | Name | Options |
| ---- | ---- | ------- |
| messager | `wechat` | `baseUrl`, `tokenEnv`, `tokenFile`, `chatIds`, `pollIntervalMs`, `timeoutMs`, `bundleGapMs` |
| filter | `ignore` / `ignore-sender` | `file` (string), `senderIds` (string array) |
| filter | `model` | Top-level `model` reference required; `options.instructions` customizes decision criteria |

### Main account status queries

Set optional `messager.mainAccount` to your personal account's exact sender ID as
reported by the adapter (for WeChat, usually `wxid_...`, rather than a display name).
The bot remains logged into its separate account. The setting belongs beside
`name` and `replyer`, outside transport `options`; omitting it disables status access.

Send the exact command `/status` in a direct chat from that account to the bot.
The server authenticates both the sender ID and direct conversation ID. Queries
from other accounts or in groups are silently ignored. Surrounding whitespace is
accepted; commands are recognized individually even inside a message bundle.

The report includes server uptime, pipeline count, queued conversations/messages,
pending status requests, delivery/failure counts, last successful delivery, and
the receiving adapter's cached polling health. It uses local observations without
model calls or additional API requests. It excludes message contents, credentials,
and configuration paths. Delivery counters include status reports and reset on
restart.

Status queries share the conversation FIFO queue and normal random **2–5 minute**
delay. Repeated pending queries in the same conversation are coalesced. A report
is sent directly to `mainAccount`, bypassing filters and the replier, and consumes
the same send slot as an ordinary reply. Commands/reports stay out of model
snapshots and conversation memory; buffered ordinary messages remain pending for
a later turn. Failed reports await a new query rather than retrying automatically.

WeChat automatically monitors the configured main account even when `chatIds`
restricts other conversations. Other messages from this account use the regular
filter/replier pipeline.

### WeChat adapter

The built-in `wechat` adapter connects to an already running, logged-in
[agent-wechat server](https://thisnick.github.io/agent-wechat/reference/api/).
It uses outbound REST requests and opens no listening ports. Login and container
setup are managed separately with agent-wechat.

Example `config.json`:

```json
{
  "chats": [
    {
      "messager": {
        "name": "wechat",
        "replyer": "my-provider/my-model-id",
        "options": {
          "baseUrl": "http://127.0.0.1:6174",
          "tokenEnv": "AGENT_WECHAT_TOKEN",
          "pollIntervalMs": 5000,
          "chatIds": ["wxid_example", "example@chatroom"]
        }
      },
      "filters": []
    }
  ]
}
```

Set `AGENT_WECHAT_TOKEN` on the machine running ChatServer. Alternatively, set
`tokenFile` to the agent-wechat token file (for example an absolute path to
`~/.config/agent-wechat/token`, expanding `~` yourself). Relative paths resolve
against the ChatServer config folder. The environment token takes precedence;
its variable name is configurable through `tokenEnv`. Tokens are read at startup.
The factory reads the token before constructing the adapter. Direct callers pass
it as a required constructor argument: `new WechatMessagerAdapter(token, options)`.
The adapter itself does not read environment variables or token files.

| Option | Default | Meaning |
| ------ | ------- | ------- |
| `baseUrl` | `http://127.0.0.1:6174` | Agent server root URL, without `/api` |
| `tokenEnv` | `AGENT_WECHAT_TOKEN` | Environment variable containing the bearer token |
| `tokenFile` | unset | Token file used when the environment token is absent |
| `chatIds` | all chats | Chat IDs to monitor, plus `mainAccount` when configured; an empty array monitors only `mainAccount`, or none when unset |
| `pollIntervalMs` | `30000` | Delay in milliseconds after a completed poll |
| `timeoutMs` | `30000` | Timeout in milliseconds for each request |
| `bundleGapMs` | `10000` | Maximum gap between consecutive messages in a bundle; `0` disables bundling |

The adapter checks login status and paginates `/api/chats`, then reads messages
for changed chats. It does not open chats or clear unread counts. Polling failures
increase the delay exponentially, up to 64 times the configured interval; success
restores the normal interval. Missing database keys may still cause the upstream
API to extract keys; the adapter cannot disable that upstream behavior.

Only incoming text and image messages with an identified sender and `isSelf: false` enter
the pipeline. Messages from before adapter startup are skipped. Cursors and
message deduplication are kept in memory; messages received while ChatServer is
stopped are not replayed after restart. Keep the machines' clocks synchronized.
Account changes reset the cursors and history cutoff.

Within each poll, incoming text and image messages are bundled for dispatch when they are
consecutive in the same conversation, have the same sender, and each timestamp is
at most `bundleGapMs` after the previous message. This applies to direct chats and
group/channel conversations. Another sender, a self message, or an unsupported
message ends the bundle. Messages in different conversations are never combined.
The bundle is dispatched when processing that poll finishes; it does not wait for
future polls.

Bundled text is joined with newlines. The adapter also supplies normalized source
`messages` with each sender, text, and timestamp, so a bundle of 30 messages counts
as 30 messages toward the snapshot limit. Metadata retains every source message
in `messages`, all `localIds`, and
`firstTimestamp`/`lastTimestamp`; singular fields such as `localId` and `timestamp`
refer to the last source message. Every source ID is still tracked for deduplication.

Replies go to the originating conversation, including groups. `reply.channel`
overrides the destination; `direct: true` sends to the originating sender instead.
The server keeps one pending entry per conversation in a FIFO queue across all
configured pipelines. New messages update its context without changing its queue
position. Conversations and context are isolated by pipeline and WeChat account.

Before selecting a conversation and building its snapshot, the server waits a
fresh random 2–5 minutes, including before the first reply. Polling continues
during the wait. Filters and the replier then see all retained incoming messages
since the last successful reply, capped at the latest 30 individual messages in
order, with their original senders and timestamps. There is no age cutoff.

A successful reply clears only the messages in that snapshot. Messages received
during generation or delivery are kept, and the conversation returns to the back
of the queue. If filters deny the snapshot, the model declines, or processing
fails, its bounded context is retained until a later successful reply. Only new
arrivals schedule another turn; unchanged snapshots and failed sends are never
retried automatically. A skipped conversation does not consume the send slot,
so the next conversation can be processed immediately.

Model processing and delivery remain sequential. Each send attempt consumes the
slot, so another random delay is required before the next attempt. The delay is
fixed in code and cannot be configured. Shutdown cancels pending delays. Replies
are text-only; incoming images are supported as described below.

The random delay does not guarantee protection from WeChat account bans.
Separate server instances do not share this in-memory limiter.
Avoid configuring multiple pipelines to monitor the same WeChat conversations,
which would cause duplicate replies.

The configured `replyer` generates the response. With `filters: []`, the reply model
decides whether a response is useful. When filters are omitted or empty, filter
evaluation is skipped entirely.

### WeChat image input

Incoming WeChat image messages (`type: 3`) enter the same conversation queue as
text. They count toward the 30-message limit, and can be bundled with adjacent
text from the same sender. Their text is represented as `[Image]`; the original
message metadata is retained separately.

Image bytes are retrieved lazily when a model filter or replier processes the
snapshot, after the normal reply delay. Polling does not fetch media. The adapter
uses `/api/messages/:chatId/media/:localId?quality=best`, with its bearer token
kept on the agent-server request. Per the [upstream media implementation](https://github.com/thisnick/agent-wechat/blob/main/packages/agent-server-rust/src/router/messages.rs),
this returns the best available cached image and may ask WeChat to download an
advertised original. It does not open chats; missing database/image keys remain
subject to the upstream server's extraction behavior.

The latest **four images per snapshot**, each up to **5 MiB decoded**, are supplied
as native Responses API `input_image` parts using base64 data URLs. PNG, JPEG,
GIF, and WebP are recognized by their file signatures. Message IDs, senders, and
timestamps identify which source message each image belongs to. Text-only turns
retain ordinary text input. Model filters and the replier share the same downloaded
image data for that turn, including across application-managed tool calls.

Both the configured reply model and any model filters that receive images must
support [image inputs](https://developers.openai.com/api/docs/guides/images-vision).
GIF inputs remain subject to the provider's animation restrictions. Images beyond
the snapshot limit are labeled omitted. Pending, expired, URL-only, oversized,
unsupported-format, and failed media responses are labeled unavailable; other
messages still proceed, and the model is instructed not to guess missing image
contents. There is no automatic media retry loop; a later turn can attempt to load
retained image references again. Video, voice, stickers, and file input are skipped.

Image descriptions, visual questions, and OCR are supported. Prompts still exclude
image/video generation and modification, and file summarization/generation/editing.
Raw image data stays in the active model request rather than conversation memory
files; the replier can retain concise visual observations as notes citing the
original source message ID. Model input images do not count toward the outgoing
150-token soft / 200-token hard text limit.

### Ignore list file

`ignore-sender` reads its sender IDs from a file named `<messager>_ignore` in the config
folder. For a registered `my-messager` adapter, that is `my-messager_ignore`:

```
~/Library/Application Support/chatserver/my-messager_ignore
```

The file holds comma-separated sender IDs. Newlines also separate entries, so one ID per
line works, and `#` lines are comments:

```
# Senders that should not get replies
client-1, client-2
client-7
```

- A missing file means nobody is ignored.
- The file is re-read when it changes (checked about once per second), so edits apply
  without restarting the server.
- Set `options.file` to use a different file. Relative paths resolve against the config
  directory; absolute paths are used as-is.
- `options.senderIds` may still be used for small inline lists. Inline IDs are combined
  with the file.
- A conversation snapshot containing any ignored sender is denied as a whole.

Chats that use the same messager type share the same file by default. Give each chat its
own `options.file` when they need separate lists.

Unknown adapter names and invalid
option values cause startup to fail with a message listing what is available.
Unknown keys are ignored with a warning; invalid values cause the server to exit with
a clear error instead of silently falling back to defaults.

### Environment

`CHATSERVER_CONFIG_DIR` selects the config folder. Host, port, and welcome-message
settings and environment overrides are no longer used. Old config keys are ignored
with a warning. Remove WebSocket chat entries from existing configurations.

### CLI options

```bash
chatserver --config_dir ./my-folder   # use a specific config folder
chatserver --print-config             # show the resolved paths and values, then exit
chatserver --help
```

`--config_dir` (also `-c`, or `CHATSERVER_CONFIG_DIR`) takes a **directory**. It must

When `--config_dir` is omitted, the per-user config folder is used and is created on

```

```

## Adapters

The server core is transport- and policy-agnostic. It depends on two adapter interfaces,
each in its own folder. Every folder has an `interface.ts` holding the contract, plus one
file per implementation. All of them are re-exported from `src/server.ts`.

| File | Contents |
| ---- | -------- |
| `filters/interface.ts` | `FilterAdapter` interface and filter chain evaluation |
| `filters/ignore-sender.ts` | `IgnoreSenderFilter` |
| `filters/ignore-file.ts` | `IgnoreFile` file-backed sender list and parser |
| `filters/registry.ts` | Name → filter factory registry |
| `messagers/interface.ts` | `MessagerAdapter` interface and message types |
| `messagers/wechat.ts` | `WechatMessagerAdapter` REST polling and text replies |
| `messagers/registry.ts` | Name → messager factory registry |
| `repliers/interface.ts` | `Replier` interface |
| `repliers/model.ts` | `ModelReplier` reply generation |

Implementations are registered by name so the config file can select them. To add your
own, register it at startup before loading the config:

```ts
import { registerFilter, registerMessager } from './server';

registerFilter('my-filter', (options) => new MyFilter(options));
registerMessager('my-transport', (options, context) =>
  new MyTransport(options, context.configDir));
```

The `chats` array in the config file then references `"my-filter"` / `"my-transport"`
by name.

### Messager adapter

`MessagerAdapter` receives inbound messages and delivers replies, so the transport can be
swapped (an app API, stdin/stdout, a queue, etc.).

```ts
export interface MessagerAdapter {
  readonly name: string;
  start(handler: (message: IncomingMessage) => void): void | Promise<void>;
  reply(message: IncomingMessage, reply: OutgoingMessage, signal?: AbortSignal): void | Promise<void>;
  stop?(): void | Promise<void>;
}
```

`IncomingMessage` carries normalized `text`, a `senderId`, an optional source `id`,
`timestamp` and `channel`, optional lazy `images`, ordered source `messages` for bundles/snapshots, pruned
conversation `memory`, and adapter-specific `metadata`. A snapshot's top-level
sender and routing metadata come from the latest arrival; its `messages` preserve
each individual author and timestamp. Source IDs and timestamps are assigned by
the server when an adapter omits them.
`OutgoingMessage` carries the reply `text`, an optional
`channel`, and a `direct` flag (direct reply to the sender instead of a broadcast).

`ChatServer` owns the configured pipelines. Construct it with
`new ChatServer(options, configDir)`, passing the resolved directory selected at
invocation, then call `await server.start()`. `await server.close()` stops the adapters.
Startup failures stop adapters already started; repeated lifecycle calls reuse the
same operation, and a closed instance cannot be restarted.

Pending conversations use one FIFO queue across the entire server, with at most
one entry per pipeline/account/conversation. The server waits for its random send
slot before taking a snapshot of up to 30 incoming source messages. Filters,
model/tool calls, and delivery finish before the next conversation is processed.
New arrivals during processing return that conversation to the back of the queue.
Context is cleared through the processed snapshot only after successful delivery;
declined or failed turns retain context but await new arrivals before reprocessing.
A failure is logged and the queue continues. Snapshots and queue state are held
in memory; summarized context and confirmed sent replies persist separately.
Shutdown cancels active delay/model/send work and discards queued work.
Messager factories receive `chatName`, `configDir`, and optional `mainAccount` as
context. Adapters may implement `getStatus()` to return cached local health for
authorized status reports; it must not issue network requests.

### Filter adapter

`FilterAdapter` decides whether an inbound message should be replied to. It returns
`FilterOutcome.Allowed`, `FilterOutcome.Denied`, or `FilterOutcome.Optional`:

```ts
export enum FilterOutcome {
  Allowed = 'allowed',
  Denied = 'denied',
  Optional = 'optional'
}

export interface FilterAdapter {
  readonly name: string;
  shouldReply(message: IncomingMessage): FilterOutcome | Promise<FilterOutcome>;
}
```

- `FilterOutcome.Allowed` — reply to the message.
- `FilterOutcome.Denied` — do not reply.
- `FilterOutcome.Optional` — let the next filter decide; if all abstain, delegate to the reply model.

Filters run in order and the first decisive result wins. If every filter abstains (or no
filters are configured), the reply model is responsible for deciding whether to respond.
There is no configuration flag for that decision. A filter that throws or produces an
invalid model decision is treated as `FilterOutcome.Denied` (fail closed). A denied
message never reaches the reply model.

```ts
import path from 'node:path';
import { ChatServer } from './server';
import { ChatServerOptions } from './config';

const configDir = path.resolve('./my-folder');
const options: ChatServerOptions = {
  chats: [{
    messager: { name: 'wechat', replyer: 'my-provider/my-model-id' },
    filters: [{ type: 'ignore-sender', options: { file: 'wechat_ignore' } }]
  }]
};
const server = new ChatServer(options, configDir);
await server.start();

await server.close();
```

`IgnoreSenderFilter` also accepts a fixed string array for simple cases.
Adapters are plain objects, so custom filters need only implement `shouldReply`
in their own module.

### Runtime models

Both `messager.replyer` and a model filter's `model` use `<provider>/<model id>`.
The provider name and the **actual model ID**, rather than its CLI display name,
must exist in `models.json` in the same config directory. The first slash separates
the provider, so model IDs may themselves contain slashes. Existing messager configs
must replace `type` with `name` and add `replyer`.

At startup, ChatServer validates the referenced providers/models and loads each
provider's API key once. The key comes from `CHATSERVER_MODEL_API_KEY` when set,
otherwise from the OS credential manager, using the same provider accounts as
`chatserver-models`. The environment override applies to all providers. No model
requests are sent during startup; they are made only for incoming messages.

The runtime uses the existing Responses API compatible client. A model filter is
instructed to return exactly `allowed`, `denied`, or `optional`. Filter calls explicitly
set `reasoning.effort` to `none`; choose a filter model/provider that supports disabling
reasoning. Unsupported settings fail closed through the existing filter error path.
Replier calls retain the provider's default reasoning behavior. The reply model
returns JSON with `reply` (boolean), `text` (string), and internal `memoryUpdates`.
On an optional filter outcome,
`reply: false` suppresses the response; an allowed outcome requires a nonempty reply
for supported requests. Filter and replier prompts ignore requests for image/video
generation or modification and file summarization, generation, or modification.
These exclusions override filter requirements; internal memory updates remain enabled.
Malformed replies and provider errors are logged without sending fallback text.

Repliers aim for a soft limit of **150 tokens**, with a hard limit of **200 tokens**
on the outgoing `text`, including URLs. The prompt requests concise replies; any
oversized reply is truncated locally before sending, preserving valid Unicode.
The application uses `o200k_base` tokenization consistently across providers, so
provider-specific billing token counts may differ. These limits apply to delivered
reply text, not the JSON envelope, memory notes, tool results, or internal reasoning.

Requests include the current conversation snapshot, sender IDs, channel, and
retained conversation memory, plus supported images as separate image parts.
Other attachment types are not sent to the model.
Individual model requests have a 60-second timeout; replies using tools have a
120-second overall deadline. Requests are cancelled during server shutdown. Failed
model requests and sends are not retried automatically.

### Conversation memory

Memory is enabled automatically. Each conversation has a JSON file at
`<configDir>/conversations/<sha256>.json`. The hash covers the adapter name,
logged-in account, and conversation ID. For adapters without account metadata,
the pipeline name supplies the account scope. WeChat memory survives restarts and
pipeline reordering for the same account and conversation.

Memory contains model-written notes categorized as `summary`, `fact`, `question`,
or `inference`, plus recent replies whose delivery was confirmed by the adapter.
Filters and repliers receive this as untrusted context alongside the latest
30-message snapshot. The model is instructed to attribute facts to senders,
distinguish inferences, resolve stale questions, and avoid repeating sent replies.

The replier returns internal updates separately from its short outgoing message:

```json
{
  "reply": false,
  "text": "",
  "memoryUpdates": {
    "notes": [
      {
        "kind": "question",
        "text": "Alice is waiting for Bob to confirm the meeting time.",
        "sourceIds": ["message:123"]
      }
    ],
    "forget": []
  }
}
```

Source IDs must refer to supplied snapshot messages or existing notes/replies.
The application derives each note's expiry from the earliest cited source;
summarizing existing notes preserves their original age. Unknown sources are
discarded. `forget` removes existing notes that are resolved, contradicted, or
replaced. Notes can be saved when the model declines to reply or delivery fails;
denied snapshots do not invoke the replier. Only the application records actual
sent replies, after successful delivery.

Entries expire after **three days**. Each conversation's serialized notes and
sent replies are capped at **1,000 tokens** in total, independently of the outgoing
150-token soft / 200-token hard limit. Individual notes are capped at 300 tokens;
oldest entries are evicted when the total budget is exceeded. This is compact
context, not a raw three-day message archive: messages dropped by the snapshot
limit before a model sees them cannot be summarized.

Expired entries are removed before model use, on startup, and during hourly
cleanup. Empty files are deleted, including those belonging to inactive
conversations. Writes use a temporary file and atomic rename. New directories
and files request owner-only permissions where supported. Malformed files are
logged and preserved for inspection; their contents are excluded from prompts.
Persistence failures are logged without turning a successfully sent reply into a
retry. Cleanup runs while the server is running and at its next startup.

### Replier tools

Repliers use application-managed function calling: the model requests a function,
ChatServer executes it, and the result is sent back to the model until it produces
the final reply JSON. No provider-hosted search tools are used. Providers and models
must support Responses API function calls and function-call outputs. Intermediate
output items, including reasoning, are preserved within each reply; they are not
retained as conversation history. See the [function-calling documentation](https://developers.openai.com/api/docs/guides/function-calling).

All four tools are enabled by default. Select a subset with `messager.tools`, or
set it to `[]` to disable tool calling for that replier:

```json
{
  "name": "wechat",
  "replyer": "my-provider/my-model-id",
  "tools": ["web_search", "read_url", "calculate", "current_time"],
  "options": { "tokenEnv": "AGENT_WECHAT_TOKEN" }
}
```

| Tool | Arguments | Behavior |
| ---- | --------- | -------- |
| `web_search` | `query` | DuckDuckGo; up to five titles, source URLs, and snippets |
| `read_url` | `url` | Title, final URL, and up to 20,000 characters of page text |
| `calculate` | `expression` | Floating-point arithmetic and selected math functions |
| `current_time` | `timezone` | Current UTC and local time; IANA zone or `null` for UTC |

Search uses [DuckDuckGo's non-JavaScript HTML results](https://duckduckgo.com/duckduckgo-help-pages/features/non-javascript),
without an API key. This is HTML parsing rather than a guaranteed search API;
rate limits, bot challenges, and page changes can make searches fail. Such failures
are returned to the model as errors. `WebSearchTool` accepts a `WebSearchProvider`
implementation so a different backend can be supplied later. Applications can
replace the default factory with `registerTool('web_search', factory)` before startup.

`read_url` supports HTML, plain text, Markdown, and JSON, including gzip, deflate,
and Brotli compression. It does not execute JavaScript, use cookies, log in, or
read PDFs. HTTP(S) requests are limited to public addresses on ports 80/443;
private/local destinations and redirects to them are rejected. Each download has
a 15-second deadline, five-redirect limit, and 1 MiB transfer/decoded size limits.
Retrieved pages are treated as source data; repliers are instructed to cite URLs
in their response text.

`calculate` supports `+ - * / % ^ **`, parentheses, scientific notation, `pi`, `e`,
`sqrt`, `abs`, `sin`, `cos`, `tan`, `floor`, `ceil`, `round`, `ln`, `log`, `exp`,
`min`, `max`, and `pow`. Trigonometry uses radians, `log` is base 10, and `%` is
modulo. Expressions are limited to 1,000 characters and 256 tokens. JavaScript and
property access are not supported.

Tool execution is limited to eight calls per reply, with at most eight tool rounds
and one final answer request. Arguments and results are size-limited; errors are
sent back to the model rather than exposed as successful results. Filters do not
receive tools. Tool work is cancelled on server shutdown.

## Models

`chatserver-models` manages OpenAI Responses API compatible providers and models. Provider
details live in `<config_dir>/models.json`; each provider's API key lives in the OS
credential manager under the provider name.

```bash
chatserver-models <command> [options]
```

| Command | Description |
| ------- | ----------- |
| `add` | Add a model to a provider and store the provider's API key |
| `test` | Send a prompt to a configured model |
| `list` | List configured providers and models |
| `update` | Change provider or model details, or rotate the API key |
| `remove` | Remove a model (and its provider once empty) |

Run `chatserver-models <command> --help` for command-specific options. Every command
accepts `--config_dir <dir>`, which defaults to `CHATSERVER_CONFIG_DIR` or the per-user
config folder.

API keys are never written to `models.json`:

| Platform | Credential store |
| -------- | ---------------- |
| macOS | Keychain (via `security`) |
| Linux | Secret Service (via `secret-tool` from libsecret) |
| Windows | Credential Manager (requires the `CredentialManager` PowerShell module) |

Credentials use the service name `chatserver-models` and the **provider name** as the
account, so every model from the same provider shares one key.

### Add a model

```bash
npm run model:add -- \
  --provider openai \
  --base-url https://api.openai.com/v1 \
  --model gpt-4.1-mini \
  --name gpt-mini
```

The provider is created when it does not exist yet. An existing provider's base URL and
API key are kept unless you pass `--base-url` or `--api-key`. When the provider has no
stored key, the key is read from `--api-key`, then `OPENAI_API_KEY`, then an interactive
prompt (input is hidden). Existing models are only replaced with `--force` or by
confirming the prompt.

`models.json` holds non-secret details:

```json
{
  "version": 1,
  "providers": [
    {
      "provider": "openai",
      "baseUrl": "https://api.openai.com/v1",
      "models": [
        { "id": "gpt-4.1-mini", "name": "gpt-mini" }
      ]
    }
  ]
}
```

### Test a model

```bash
npm run model:test -- --provider openai --name gpt-mini --prompt "Say hello."
```

Add `--json` to print the raw API response, or `--timeout <ms>` to change the 60-second
request timeout. The key comes from `CHATSERVER_MODEL_API_KEY` or the credential manager.

### List, update, and remove

```bash
npm run model:list --

npm run model:update -- --provider openai --base-url https://api.openai.com/v1
npm run model:update -- --provider openai --api-key sk-...          # rotate the key
npm run model:update -- --provider openai --name gpt-mini --model gpt-4.1
npm run model:update -- --provider openai --name gpt-mini --new-name mini

npm run model:remove -- --provider openai --name gpt-mini
```

When `remove` deletes a provider's last model, the provider entry is removed too and its
API key is deleted from the credential manager.

`list` prints a table with provider, model name, model id, and base URL; add `--json` for
raw JSON. `update` only changes the options you pass and fails when none are given.

When installed as a CLI the binary is `chatserver-models`, for example
`chatserver-models add --model gpt-4.1-mini`.

## Installing as a CLI (npx)

The package exposes a `chatserver` executable (`"bin": { "chatserver": "dist/index.js" }`),
so it can be invoked with `npx`.

### Install into another project

From the directory you want to use the command in (it must contain a `package.json`):

```bash
npm install /path/to/ChatServer
npx chatserver
```

This symlinks the local project into `node_modules`, and `npx` resolves the `chatserver`
binary from there. Because `dist/` is git-ignored, build once in the ChatServer directory
first (`npm run build`). The `prepare` script normally does this automatically, but some
npm versions block install scripts by default — run the build manually if prompted.

### One-off invocation without installing

```bash
npx --yes --package=/path/to/ChatServer chatserver
```

`--package` also accepts a packed tarball:

```bash
cd /path/to/ChatServer
npm pack                                  # creates chatserver-1.0.0.tgz (dist/ only)
npx --yes --package=/path/to/chatserver-1.0.0.tgz chatserver
```

### Make it globally available

```bash
cd /path/to/ChatServer
npm link
npx chatserver
```

Environment variables still apply in every form, for example:

```bash
CHATSERVER_CONFIG_DIR=/path/to/config-dir npx chatserver
```

## Debugging

Two debug configurations are provided in `.vscode/launch.json` (press **F5** to start):

- **Debug Chat Server (ts-node)** — runs `src/index.ts` directly with `ts-node`; no build step required.
- **Debug Compiled Output (node)** — runs the webpack bundle at `dist/index.js`; automatically runs the `build` task first.

The webpack configurations emit source maps whose paths resolve back to `src/`, so
breakpoints set in your `.ts` files are hit correctly in both configurations.

## Linting

ESLint is configured in `eslint.config.mjs` with a TypeScript ruleset similar to
[`microsoft/vscode-cmake-tools`](https://github.com/microsoft/vscode-cmake-tools).

Check the codebase:

```bash
npm run lint
```

Automatically fix fixable issues:

```bash
npm run lint:fix
```

The configuration uses type-aware linting, so it can report issues such as floating
promises and misused promises. The ESLint VS Code extension will also surface these
diagnostics inline.
